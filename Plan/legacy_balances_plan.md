# Implementation Plan: Legacy Balances & Settlements

بناءً على التعديلات الدقيقة، سنقوم بإنشاء النظام للتعامل مع الفواتير المفتوحة التاريخية بشكل ذكي يدعم التسويات الجزئية والكلية.

## Proposed Changes

### 1. Database Schema
سنقوم بإنشاء جدول جديد في قاعدة البيانات (Supabase) باسم `debit_OB`.
- **Columns (All Capitalized):**
  - `ID` (Primary Key)
  - `CUSTOMER_CODE` (كود العميل فقط)
  - `INVOICE_DATE` (تاريخ الفاتورة)
  - `INVOICE_NO` (رقم الفاتورة القديمة / المرتجع / الخصم)
  - `DEBIT` (مدين - لفواتير المبيعات)
  - `CREDIT` (دائن - للمرتجعات والخصومات الأصلية)
  - `SETTLED_AMOUNT` (المبالغ التي تم تسديدها لاحقاً لتسوية هذه الفاتورة)
  - `STATUS` (حالة التسوية بدلاً من الصح والخطأ، وقيمها: `OPEN`, `PARTIAL`, `SETTLED`)

### 2. Backend Services
- إنشاء دوال للتعامل مع الجدول الجديد `debit_OB` وإجراء التسويات.

### 3. User Interface (UI)
- **شاشة "Legacy Balances" (أرصدة افتتاحية):** 
  سنضيف شاشة جديدة (Tab) داخل قسم الـ Debit.
  - تسمح برفع ملف Excel لمرة واحدة.
  - تعرض جدولاً بالفواتير.
  - عند الضغط على "تسوية"، سيطلب منك السيستم إدخال **المبلغ المسدد**.
  - إذا كان المبلغ المسدد يساوي المتبقي من الفاتورة، تتحول الحالة إلى `SETTLED` (تسوية كلية).
  - إذا كان أقل، تتحول الحالة إلى `PARTIAL` (تسوية جزئية)، ويُحفظ المبلغ في `SETTLED_AMOUNT`.
  
### 4. Statement Generation & Partial Payments Logic
- **في كشف الحساب (PDF Engine):**
  - السيستم سيقوم بجلب الفواتير التي حالتها `OPEN` أو `PARTIAL` فقط. الفواتير الـ `SETTLED` لن تظهر نهائياً.
  - **طريقة عرض الفاتورة الجزئية (Partially Paid):** ستظهر الفاتورة برقمها وتاريخها، وسيظهر الجانب الـ `DEBIT` كما هو، بينما في جانب الـ `CREDIT` سيتم دمج (الـ Credit الأصلي + الـ SETTLED_AMOUNT)، مما يجعل العميل يرى بوضوح قيمة الفاتورة وقيمة ما سدده منها والرصيد المتبقي لها.
